## Payroll contracts

Standalone routes require manager/owner; delete/revert require owner. Employee-prefixed payroll also requires manager/owner. Both generation APIs call the same draft builder and share salary history; only the standalone payout lifecycle posts payroll journals. Employee PayrollService no longer pays cash or sweeps a wallet during generation.

| Method/path | Exact consumed body/query | Current source behavior |
| --- | --- | --- |
| `POST /payroll/run` | `month`, `year`; optional `employeeId`, `daysWorked`, `manualAdjustment`, `adjustmentReason`, `overtimeHours`, `overtimeAmount`, `extraDays`, `extraDayAmount`, `advanceDeduction` | Shared builder validates month/year and finite nonnegative worked days ≤ month length; locks active employees and existing history. Upserts Pending employee/month/year drafts and components in one transaction, skips Approved/Paid rows, posts no journal. Stores adjustment reason, month length, paid-leave days and missing-attendance flag. Returns `{ success, data }`. |
| `GET /payroll/monthly` | Query `month`, `year` | Array of existing history rows with employee details and aggregate outstanding advances; no default period. |
| `POST /payroll/approve` | `id` | Pending → Approved; invalid/repeated transition returns 409. |
| `POST /payroll/payout` | `id`, `payment_mode`, `payment_date`, `paid_by` | Lifecycle locks employee/history, requires Approved, checks writable date/account, recovers advances and posts positive net cash or negative net shortfall before marking Paid, all on the caller's transaction. Zero net posts no cash. Missing date/mode default now/Cash. Payer text and authenticated `paid_by_user_id` are stored separately. Returns `{ success, record, repayment_journal_id }`. Invalid transition is 409. |
| `POST /payroll/revert/:id` | `targetStatus`, nonblank `reason` | Exactly Paid → Approved or Approved → Pending. Paid revert rejects any unreversed shortfall settlement, then reverses payroll/shortfall sources and recovery allocations, marks shortfalls Reversed, clears payout metadata and writes payroll audit in one transaction. |
| `DELETE /payroll/:id` | Nonblank `reason` | Uses the correction helper's day → employee → history lock order; Paid deletion uses the same lifecycle reversal, deletes components/history and stores the prior row in audit metadata. |
| `POST /employees/payroll/run` | Same shared-builder fields as `/payroll/run` | Creates the same Pending drafts, skips Approved/Paid rows and posts no journal. Returns `{ success, data, netPay, earnedSalary, salaryHistoryId }` for the first returned draft. Its controller uses the same domain status mapping as standalone payroll; recovery requested above zero outstanding debt rejects with 400. |
| `GET /employees/payroll/monthly` | Query `month`, `year`, default current period | `{ month, year, data }`, all active employees including those without history; base salary/net defaults differ from standalone list. |

Shared attendance calculation earns Present=1, Half-Day=0.5 and employee-matched attendance linked to an Approved Paid leave=1; the paid-leave check runs first so a day is counted once. Other statuses and Unpaid leave earn zero. **No rows still means a full month**, now persisted as `attendance_missing` and shown in Payroll. Explicit days for a specific employee override attendance; that path records zero paid-leave days and no missing flag. Actual calendar month length controls proration. Salary structure replaces base salary and prorates both earnings/deductions; effective dates and inactive component metadata are not filtered. Overtime and extra pay use submitted amounts, not a server-computed hours/rate formula.

Gross = prorated earnings + overtime amount + extra amount + manual adjustment. Net = gross − component deductions − advance deduction, rounded to signed cents. Default recovery is the full positive outstanding advance balance; explicit recovery may exceed salary but cannot exceed actual outstanding debt. Draft `calculated_salary` stores gross including adjustment; deductions JSON stores component total and allowances stays empty. Both APIs persist `manual_adjustment`, `adjustment_reason`, `total_days_in_month`, `paid_leave_days` and `attendance_missing`. For salary 30,000 and advance 40,000, current source generates net −10,000, recovers 40,000 and records a 10,000 shortfall rather than a negative cash line.

Current lifecycle recovers FIFO by created time/ID from positive `salary_advances.balance_remaining`, adjusts `total_repaid`, recovered/remaining/flag/status, records `payroll_recovery_allocations`, and adds a Repayment ledger row plus recovery journal. Linked installments also receive source-journal schedule allocations. A positive leftover is rejected when positive modern advances participate; ledger-only older advances remain recoverable. Zero net skips cash journal lines and can complete recovery. Payout checks aggregate outstanding before recovery. Reversal restores exact advance and installment allocations, including `total_repaid`, and marks allocation rows reversed rather than deleting them. It selects AdvanceRepayment sources only when a matching employee ledger row has the Payroll tag, isolating cash-request IDs from salary-history IDs.

Payout and delete/revert take day, employee, then salary-history locks. The correction helper rereads the history under lock and returns 409 if its payment date changed. [Integrity regressions](../audit/phase2/fixes/integrity-regressions/results.json) pass deduction-bearing payout → revert → payout restoration, a colliding manual repayment from another employee, and one same-row concurrent payout/correction case. These checks do not establish cross-API payroll generation safety or every lock race.

The routed [Payroll page](../../client/src/pages/Payroll.jsx) uses standalone routes. Its payer-name input is accepted by migration 043's text column and the earlier PAY-009 browser assertion passes in hr-first. The editing form now initializes days with nullish fallback and submits parseFloat, preserving zero/fractional input in source. It shows signed amounts, employee debt, paid-leave days and missing-attendance assumptions. Current browser assertions are defined in completion.spec.cjs; consult the corresponding completed results for reached scope. [usePayroll.js](../../client/src/hooks/usePayroll.js) remains an unused export with mismatching approve/payment URLs.

### Payroll shortfall settlement

[Migration044](../../database/migrations/044_workflow_completion.sql) gives negative payout a separate1110 employee receivable, shortfall row and authenticated actor. Shortfall and settlement history has no salary-history FK and survives salary deletion; successful correction leaves it marked Reversed. It is separate from advance1100 debt and wallet balances.

| Method/path | Input | Current source behavior |
| --- | --- | --- |
| `GET /payroll/shortfalls` | None | Manager/owner; all shortfalls, employee names, outstanding amount and nested settlement history. Reversed rows remain visible. |
| `POST /payroll/shortfalls/:id/settle` | Positive `amount`, required nonblank `reference`, optional `paymentMode` (Cash default) | Manager/owner; normalizes amount to cents and rejects a rounded zero, then takes day/account and shortfall locks. Rejects excess/non-Open debt; matching unreversed reference retries return the existing receipt, conflicting reuse409. Dr selected cash/Cr1110 and receipt/settled total/status commit together. |
| `POST /payroll/shortfalls/:id/settlements/:paymentId/reverse` | Nonblank `reason` | Owner only; checks exact shortfall/payment, locks and reverses the receipt at its journal date, marks it reversed and restores Open outstanding. Repeated reversal is unchanged. |

Payroll revert/delete refuses a shortfall with `settled_amount > 0`; reverse its receipts explicitly before correcting payroll. Settlement comparisons, posting and persisted totals now use the normalized cent amount; the PAY-004 completion case covers a 0.999 receipt settling a 1.00 shortfall and matching normalized retry.

Schedules use integer cents with remainder in the last installment and UTC month-end clamping; zero-value installments start Paid. Stored `monthly_deduction` remains a rounded equal amount and can differ from the final installment. Payroll's default recovery is still full outstanding debt, rather than the monthly scheduled amount. Manual and payroll recovery allocate each linked advance across open installments in month-number order, updating Pending/Partial/Paid and `advance_schedule_allocations`; payroll reversal restores only allocations from its source journal. [Migration045](../../database/migrations/045_advance_schedule_sync.sql) links modern advances to requests and supplies schedule recovery state/allocation history. Both approval namespaces use the same disbursement service; the scheduled-advance completion case covers manual partial recovery, payroll/revert and repayout.

Transfers consume `{ toUserId, amount, description, mode, targetType }` at `/finance/transfer/safe-to-user` or `{ fromUserId, amount, description, mode, targetType }` at `/finance/transfer/user-to-safe`; missing source user defaults current user. `targetType: employee` creates and auto-approves the cash advance/repayment on **one transaction**, so failure does not leave Pending data. User transfers lock account rows, journal linked destination/source accounts and insert wallet history with In/Out direction, before/after balance and actor in the same transaction. Central entities reject invalid/same-account lines. Negative wallet balances are retained under the current tracking assumption rather than rejected. `GET /finance/transfer/history` requires FINANCE_READ and returns wallet balances/positive overdraft magnitudes plus the latest 500 history rows. Owner Equity transfer classification remains a separate decision.

## Attendance, leave and employee changes

Both `/attendance/bulk` and `/employees/attendance/bulk` consume `{ date, records: [{ employee_id, status }] }`, require manager/owner, and atomically upsert status on employee/date. Shared validation checks supported statuses, locks active employees in ID order and existing attendance, and rejects locked/leave-linked rows with 409. Extra overtime/check-in body fields remain ignored, and bulk writes do not create governance audit/change-request rows.

GET attendance uses `date`, active employee left join and nullable unmarked attendance IDs. Only standalone attendance provides `/last-dates` and `/calendar?startDate=...&endDate=...`; calendar now counts active employee records only, with missing/partial/complete status. It still does not call the SQL governance calendar function or report locks.

Leave body is `{ employee_id, leave_type, start_date, end_date, reason }`; first four required. Type must be one of the five UI choices: Sick, Casual, Paid, Unpaid, Emergency; invalid types return400 before insertion. Database enforces date range and generates inclusive total_days. GET supports `status`, overlapping `startDate/endDate`, `employeeId`; employee/date lookup routes also exist. Staff list/create/employee-history/delete are constrained to their linked employee, and date lookup also filters staff to their linked employee. Pending approval/rejection/deletion are conditional; approval conflicts return409 and reversed dates400. Approval locks employee, rejects existing locked/leave-linked attendance, writes linked **Absent** across the inclusive range and audits it. Payroll now consults the approved leave link to distinguish Paid salary days from Unpaid absence. Entitlement/accrual rules remain separate from this implemented pay distinction.

[EmployeeService](../../server/src/modules/employees/EmployeeService.js) consumes full_name/first_name/last_name/position/age/gender/phone_number/base_salary/status/role/govt_id_type/govt_id_number. Creation serializes MAX-ID code allocation with an advisory lock; the controller still requires truthy salary, although the service accepts zero. Update uses nullish values so zero/empty fields persist, locks the employee, and history uses persisted values for salary/position/role/status. Deletion dependencies now map to 409; employee list remains token-only with staff salary masking. Changing employee role does not change the user's login role.

## Finance contracts, accounts and reversals

Finance routes use FINANCE_READ/WRITE. Vendor routes require FINANCE_READ; payment POST also requires FINANCE_WRITE. [PaymentModeService](../../server/src/modules/finance/PaymentModeService.js) resolves active canonical names **or display labels**, case-insensitively, and normalizes Bank Transfer to bank. Its separate getPaymentMode/validatePayment methods still match names only; payroll/advances do not enforce reference requirements. Canonical accounts: cash=1000, bank/cheque/card=1010, upi=1020, manager_float=1030.

1100 is employee advance receivable, 1110 payroll shortfall receivable, 1120 customer order receivable, 5000 COGS, 6000 Salaries Expense, 6100 Labor Costs, 6200 inventory adjustment expense and 2100 sales tax payable. Tracker no longer uses 1100 as bank/cash or 5000 as payable. Migration 043 supplies 7000/7100 and expands vendor Card/Bank CHECK values;044 supplies the new shortfall/customer/tax/adjustment accounts. POS now records both inventory_transactions and stock_movements for sales, alongside order/payment, journals and one KDS ticket, atomically.

POS consumes items `{ id, qty }` with unique menu IDs/positive integer quantities and uses stored prices. `discount` is a fixed currency amount allocated proportionally across item bases before tax; active tax rates use fractional multipliers and their configured account (fallback 2100). Order `type` is Dine In/Delivery/Pick Up; table number applies to Dine In, while customer details and notes persist. Due takes no cash; Part consumes positive `amountPaid < total` and optional `partialPaymentMode`; customerPhone is optional for every mode, including outstanding orders. Initial paid and remaining amounts reconcile to the order total.

`POST /orders` accepts an optional Idempotency-Key scoped to the actor. Same-key/same-body retries return the saved response; changed-body reuse409. `GET /orders` returns the latest 500 orders with customer, outstanding and payment history. `POST /orders/:id/payments` requires an Idempotency-Key plus positive `amount`/optional `paymentMode`/`reference`; it locks the order, rejects excess collection and atomically posts1120 settlement, receipt and Paid/Part status. Full-order refund is provided by the source-linked correction route; see [refund contracts](corrections-and-valuation.md). These API paths have POS_ACCESS; permissions do not enforce customer or order ownership.

`POST /inventory/adjustments` consumes inventory_item_id, signed nonzero quantity_change and nonblank reason; INVENTORY_WRITE. It rounds quantity to four decimals, locks stock, rejects negative resulting inventory, and records carrying-value changes, actor, before/after quantities, StockAdjustment journal (when value is positive), stock movement and inventory transaction atomically. GET returns the latest 500 adjustments. Recipe edits under `/inventory/recipes/:id` lock the menu and validate unique existing ingredients with positive quantities; POS then uses the stored recipe for stock/COGS.

Ordinary inventory creation inserts zero stock then records positive initial stock through the same adjustment service. Updates lock the item, post quantity difference using carrying value, then record/journal requested cost × resulting quantity minus prior carrying value; unchanged rounded-cost edits preserve the exact book value, all on one transaction. [Migration046](../../database/migrations/046_stock_valuation_history.sql) supplies stock_revaluations history and normalizes existing outbound movement signs. Zero-cost PO receipts still update stock, movements and received quantities, while current source skips supplier debt/journals when total cost is zero; its latest regression passes the final full audit.

Tracker create/post and undo/repost run on one client. Update accepts all create fields including mode, validates old/new writable dates/accounts, reverses unreversed source journals, inserts compensating vendor ledger rows, marks old payment rows Reversed, and posts replacements. Update/delete now reread the transaction under FOR UPDATE after the initial day lock, revalidate its current date/account and return409 if the date changed. Update validation and unchanged comparisons use that locked row. Delete reverses before deleting the transaction. Repeated unchanged updates return existing data. GET filters date/type or startDate+endDate. Keyword mapping selects Expense records and delegates to this update path. Current competing-correction assertions are defined in completion.spec.cjs; the final full audit passes that competing-correction subcase.

Pending bills commit only the source bill; approved stock receipt, liability and journal share one transaction. Rejection returns exact quantity/value and reverses financial sources, refusing insufficient stock/value or settled debt. PO receipts use cent-accurate weighted average value. See [corrections and valuation](corrections-and-valuation.md).

Central entities round each debit/credit to cents before line and aggregate validation, rejecting invalid dates/nonfinite values, zero lines, both-sided/negative rounded lines, fewer than two distinct accounts and unequal cent totals. The subcent multi-line imbalance is now rejected in source; completion.spec.cjs defines its unchanged-state regression. JournalService checks accounts and obtains a finance-day advisory lock plus selected account closures; a supplied client owns the enclosing transaction. The shared guard rejects both Locked and Closed financial periods. Balance query preserves zero-activity accounts, includes the entire as-of date and returns credit-positive Liability/Revenue/Equity. Reversal locks the original and returns an existing Reversal, uses the supplied caller transaction, and never edits original lines. The compatibility journal-delete path now reverses a journal with no reference_type; linked sources return409 and must use their own correction workflow. References remain unenforced TEXT links; no DB-level journal balance/source uniqueness constraint exists. Importer SQL still bypasses central entities.

Closure GET `/finance/daily-balance/:date` accepts type/accountCode query; close body is `{ date, type, actualClosingBalance, accountCode }`, reopen `{ date, type, reason, accountCode }`. Defaults Counter→1000, other types→1030. Close locks account/date, recalculates actual-day movements, journals variance and carries opening forward only to an Open next day. Movement filtering retains journals with null reference types and excludes CashVariance plus its reversals. Reopen locks the exact account/date, reverses variance on the same client/date with a narrow closed-day bypass, clears actual/payout closure fields and audits atomically. Snapshot fields stay distinct from recalculated expected balance. ADMIN is still absent in permissions, so current owner bypass supplies reopen access while managers are denied.
